# Mission Reflection

Completing this lab gave me a picture of why containerization has become the standard for modern cloud‑native applications. The obvious difference I saw was speed. Installing and booting an operating system on a Virtual Machine normally takes several minutes because the hypervisor must start an entire guest OS load drivers and start system services before any program can run. In contrast deploying the Nginx container took seconds. Docker did not need to boot an operating system; it simply started the Nginx process on the host’s existing kernel. That difference alone shows why containers are more efficient for scaling applications quickly.

Port mapping was another idea that became clearer when I practiced. When I ran `docker run -d -p 8080:80 --name my-nginx nginx` the `-p 8080:80` flag was needed because a container is isolated from the host machine by default. Nginx inside the container listens on port 80. That port is not automatically reachable from outside the container. By mapping host port 8080 to container port 80 I created a bridge so that a request to `localhost:8080` on my machine would go to port 80 inside the container. The `curl http://localhost:8080` command proved that this mapping worked.

I also learned that containers are temporary by design. When I ran `docker rm my-nginx` after stopping the container any data or changes made inside the container’s layer were permanently removed, because nothing was set up to keep data outside the container. I actually saw this happen in life. My KillerCoda session reset partway through the lab and the `my-nginx` container I had created earlier was gone. I had to redeploy it before I could finish the lifecycle commands. This experience showed me how disposable containers really are and why anything that must keep data, such as a database needs Docker volumes or bind mounts to store data outside the container’s lifecycle.

Thinking about this from a DevOps perspective containerization changes the relationship between developers and IT operations. Because a container holds the application and all its dependencies the "it works on my machine" problem disappears. The exact same image that a developer tests locally is the image that is deployed to production. This closes the gap between writing code and running it reliably at scale. It makes automated deployment pipelines easier to build and trust.

Moving from labs on cloud fundamentals and multi‑cloud comparisons into hands‑on container deployment shows a clear progression, toward practical cloud‑native skills. Each lab folder records not what I did but also why it matters. This is the kind of evidence I want future employers or instructors to see when they review my work.
